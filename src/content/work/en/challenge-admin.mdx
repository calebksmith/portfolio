## Problem

[Challenges](/work/challenges) worked; running one didn't. Every challenge meant
a request to us — configure it, write the invitation, remember the reminders,
work out who won. A feature that needs its vendor every time it runs is a
feature that runs rarely, and a challenge's value is in repetition.

> **The call:** design it second, on purpose. The admin tool came after
> challenges had run, so its shape came from watching real admins rather than
> guessing. And it stayed web-only: setting up a challenge is a sit-down task
> done once, not something worth making portable.

## What I did

- **A creation flow customers' own leaders can use:** type, dates, prizes, and
  the rules each type needs, like maximum team size.
- **A raffle selector.** Entries build up per participant through the run; at
  the end an admin draws a winner instead of exporting a spreadsheet and
  trusting it.
- **Emails that run off the challenge itself.** Creating one sends the
  invitation, reminders go out during the run, and a results email names the
  winner.

## Outcome

- Organizations have run more than three challenges each, on average, over two
  years, and monthly admin users grew 143% between January and September 2026.
- The emails go out whether or not anyone remembers them — which is what keeps a
  month-long challenge alive in week three.
- Prize selection is a button rather than a spreadsheet and a promise.

**Who did what:** I led design and UI. Engineering built the tool and the
automated sends; product management and leadership shaped what an admin can
configure.

## Problem

Vimocity ships web, iOS, Android, and Windows apps, and each had drifted into
its own patterns. VimUI started as a thorough Figma system — published
libraries, variables and modes, versioned releases. The cost wasn't the tool.
Every change happened twice, in Figma and then in code, and the second half
meant pulling a developer off their work to translate the file.

> **The call:** retire the Figma file. Once we prototyped in real components,
> it was a second copy of something that already existed. That was a decision
> made from inside the tool, not an escape from it — knowing a tool well is what
> tells you where it stops paying.

## What I did

- **Built 50+ components** as atoms, molecules, and organisms on shadcn/ui and
  Radix — some close to the originals, some rewritten for what we needed.
- **Tokenized color, type, spacing, and sizing**, and removed hardcoded values
  from the frontend.
- **Built accessibility into the components** — keyboard support, contrast in
  both modes, touch targets, reduced motion — so every feature inherits it.
- **Released it in versions**, so apps can test a change before it lands.
- **Bridged the gap while it lasted:** fed designs to Claude Code through
  Figma's APIs, which sped up the handoff before it removed it.

## Outcome

- Reusable component use rose from about 10% to 80–90% of frontend code.
- Token use went from 0% to 99%; the remaining 1% is deliberate overrides.
- Changes happen once, in code. A new page is assembly, not construction.

## What it doesn't cover

The components are the web app's; mobile and desktop carry their own. Tokens
reach all four platforms, but only the web app reads them directly — the others
get them copied by hand, so consistency holds by discipline rather than by build
step. Generating them from one file is the next move.

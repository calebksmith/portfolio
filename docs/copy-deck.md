## 4.1 — Design rules that enforce themselves
*Design systems · AI tooling · 2025–2026*

**Problem**
A design system only works if people follow it. Ours was well built but drifting: components got used incorrectly, raw color values slipped into code, and catching it depended on me reviewing everything. That made design the bottleneck. AI coding tools made it worse — they generated plausible code fast, and none of it knew our rules.

**What I did**
- Wrote the component standards down in one place, covering structure, tokens, typing, accessibility, documentation, and versioning.
- Extended the same approach to the product itself, with page-level rules covering token use, accessibility requirements, loading states, and responsive breakpoints.
- Turned both sets of standards into automated checks that run before code merges, so violations are caught by the system rather than by a person.
- Loaded the same standards into our AI coding tools, so generated components and pages follow the rules by default.
- Kept all of it in sync from a single source, and maintain it as the system changes.

**Outcome**
- One standard, enforced three ways: written for people, checked by automation, loaded for AI.
- Design stopped being a bottleneck — the full team can build production-quality interfaces.
- Reliance on outside design help dropped substantially.
- Prototyping opened up to people who aren't designers.

**Why it matters**
Most teams are adding AI to their workflow without deciding what "correct" means first. Writing the standard is the hard part. Enforcing it is what makes it hold.

## 4.2 — VimUI: a design system across four platforms
*Design systems · 2022–present*

**Problem**
Vimocity ships a web app, iOS and Android apps, and a Windows desktop app. Each had drifted into its own patterns. The design system lived in Figma, which meant designers had one source of truth and engineers had another.

**What I did**
- Moved the system out of Figma and into the codebase, where the components engineers use are the components the system defines.
- Built 51 components organized as atoms, molecules, and organisms, documented in Storybook.
- Established tokens for color, type, spacing, and sizing, and removed hardcoded values from the frontend.
- Made accessibility a property of the system rather than a per-feature task: keyboard support, contrast in light and dark modes, minimum touch targets, and reduced-motion support built into the components themselves.
- Set up versioned releases so consuming apps can test changes before they land.

**Outcome**
- Reusable component use went from about 10% to 80–90% of frontend code.
- Token use went from 0% to 99%.
- One visual language across four platforms.
- Building a new page became assembly rather than construction.

**See it:** the component library is public at vimui.vimocity.com

## 4.3 — Rebuilding the web app
*Front-end · Platform migration · 2026*

**Problem**
Our web application had been built up piecemeal over years. The code was inconsistent, slow to change, and increasingly hard to keep visually coherent. Rebuilding it meant rebuilding every page — and the product had to keep running the whole time.

**What I did**
- Rebuilt each existing page and feature on Next.js, TypeScript, and Tailwind, using the component library.
- Connected the new pages to existing APIs so behavior stayed intact.
- Worked page by page rather than all at once, so the migration could ship in pieces.
- Handed each rebuilt section to engineering for review and hardening.

**Outcome**
- The entire web app now runs on one modern, consistent codebase.
- Visual consistency with the mobile and desktop apps.
- Faster to build on: new features assemble from existing components.
- The migration ran alongside normal product work rather than replacing it.

## 4.4 — One login for three platforms
*Product design · Cross-platform · 2025*

**Problem**
Vimocity runs on web, mobile, and desktop, and each had its own login and account creation flow. Three codebases meant three sets of bugs, three things to update, and inconsistent experiences. Account creation was also our most common support issue.

**What I did**
- Designed a single web-based login and account creation flow.
- Surfaced it inside the mobile and desktop apps through a web view, so all three platforms use the same flow without duplicating it.
- Added multi-factor authentication and modern security handling.
- Reworked the flow itself based on where people were getting stuck.

**Outcome**
- Account creation support tickets dropped by over 80%.
- Three flows became one to maintain.
- Consistent sign-in across every platform.
- Security improved without adding friction.

**Trade-off worth naming:** a web view is not a native experience. We accepted slightly less native polish in exchange for one flow instead of three — the right call for a small team, and worth revisiting at a larger one.

## 4.5 — Challenges: designing for repeat behavior
*Product design · Behavior change · 2023–2024*

**Problem**
Vimocity helps people move more during the workday. The product only works if people come back — a single visit changes nothing. We needed something that made movement social and repeatable, without turning it into a chore or a surveillance tool.

**What I did**
- Defined three challenge types: personal targets, team targets, and team leaderboards — so people could opt into competition or avoid it.
- Designed the flows across mobile and web, and integrated them with the desktop reminder app.
- Connected challenges to daily movement targets, so everyday activity counted toward something.
- Tested with customers and non-customers to check the mechanics motivated rather than pressured.

**Outcome**
- Movement became a shared activity rather than an individual task.
- Daily reminders now ladder into a longer-term goal.
- The feature works across all three platforms from one set of rules.

**Design note:** the hardest decision was making competition optional. Leaderboards motivate some people and alienate others, especially in a health context tied to work. Personal targets let people participate without being ranked.

## 5.1 — Theme and color page

**Heading:** Themes and contrast

**Intro:**
> Every color on this site comes from a token, and every token pair is measured. Switch themes or modes and the numbers below update — including the ones that would fail.

**Section label:** Current theme
**Section label:** Contrast pairs

**Column headers:** Pair · Ratio · AA · AAA

**Explainer (small type, below the table):**
> Contrast is measured between a surface and the text or icon drawn on it, not between individual colors. Pairing them in the token layer means a component is legible in every theme without anyone remembering which color goes where.
>
> WCAG AA requires 4.5:1 for body text and 3:1 for large text. AAA requires 7:1.

**High contrast theme description:**
> Built to clear AAA on every pair, for anyone who needs more separation than the default themes provide.
